# ChatGPT Card Manager v0.7

## v0.7 展开/收起动画修复

- 修复展开时先从左上角飞到鼠标卡片的问题。原因是 v0.6 在切换到 `position: fixed` 后，`left/top/width/height` 已经处于 transition 状态，浏览器可能先从 `auto`/静态位置插值到卡片坐标。
- v0.7 改为真正的 compositor-only FLIP：先测量鼠标卡片的原始屏幕矩形，再把真实卡片无动画地布局到最终大卡片矩形，随后用 `translate3d + scale` 把视觉像素反向压回原卡片，最后只动画 `transform` 到 1。第一帧与鼠标悬停卡片完全重合。
- 展开过程中不再动画 `left/top/width/height`，避免 layout/reflow 导致的抖动和掉帧。
- 收起同样改为纯 `transform` 动画，并且可以从“展开动画尚未结束”的当前视觉位置直接反向收回。
- 收起时先冻结当前实际像素，再用约 360ms 的 compositor 动画回到原卡片占位位置，结束后才恢复普通 grid 定位，解决 v0.6 收缩卡顿/提前 snap 的问题。
- 保留 500ms 悬停触发、6–9 卡片展开面积、轻微背景模糊、正文缓存和 429 保护。

本地运行的 Chrome / Edge Manifest V3 扩展，用卡片方式批量管理 ChatGPT 历史对话。

## v0.5 新增：手动加载控制

为了进一步降低请求过多的概率，v0.5 默认关闭正文的自动后台网络预读。列表仍会先显示，正文优先使用 IndexedDB 本地缓存；未缓存正文只会在以下情况读取：

- 鼠标悬停卡片 500ms 后按需读取。
- 点击 **“加载当前页”**：顺序读取当前滚动视口内可见卡片的正文。
- 选择 **10 / 30 / 50 / 100 / 全部** 后点击批量加载按钮。

批量读取始终保持单并发，并额外控制请求间隔。手动批量正文读取之间至少约 4.5 秒，不会把几十个详情请求同时发出去。

### “加载当前页”

只处理当前 Chat Deck 内容区里真正可见的卡片。已经在 IndexedDB 中缓存的卡片直接恢复，不产生网络请求。

### “加载 N 个”

下拉可选：

- 10
- 30
- 50
- 100
- 全部

如果当前列表元数据还不够，会先安全地继续读取会话列表，再按顺序加载正文。搜索状态下则只针对当前筛选结果。

## v0.5 新增：醒目的请求过多提示

如果 ChatGPT 返回 HTTP 429，界面不再把 `429` 当成普通错误直接展示。

顶部会出现醒目的提示栏：

> 请求过多，请稍后再试

同时显示大致剩余冷却时间，并说明：

- 当前批量请求已经暂停；
- 本地缓存仍然可以正常浏览；
- 冷却结束后重新点击加载即可。

所有用户可见的列表、正文、归档和删除错误都会把 429 转换成“请求过多，请稍后再试”，不会再只出现一个状态码。

## 更保守的限流策略

- 正文并发：1。
- 普通正文请求最小间隔约 3.2 秒。
- 手动批量正文请求额外保证约 4.5 秒间隔。
- 自动正文后台预读：默认关闭。
- 会话列表请求最小间隔约 1.8 秒。
- 删除 / 归档最小间隔约 2.2 秒。
- 一旦收到“请求过多”响应，本轮批量正文任务立即停止，不在后台连续重试。
- 删除 / 归档遇到请求过多时同样停止本轮后续操作。
- 冷却时间继续写入 localStorage，多 ChatGPT 标签页共享。
- 支持 Web Locks 的浏览器会继续串行预留请求时隙。

## 其他功能

- 卡片式历史会话浏览。
- 鼠标停留 500ms 后展开。
- 展开浮层约占 6~9 张普通卡片面积，不挤动其他卡片。
- 展开后背景轻微模糊。
- 左侧“对话速览”，右侧完整消息时间线。
- IndexedDB 本地正文缓存。
- 创建时间优先使用真实 `create_time`，必要时回退到最早消息时间。
- 单条删除、批量选择、批量归档、批量删除。
- Alt + M 打开/关闭。

## 安装 / 更新

1. 解压 ZIP。
2. Chrome 打开 `chrome://extensions/`；Edge 打开 `edge://extensions/`。
3. 开启“开发者模式”。
4. 首次安装：点击“加载已解压的扩展程序”。
5. 已安装旧版：用 v0.5 目录覆盖旧目录，然后点击扩展的“重新加载”。
6. 刷新 `https://chatgpt.com/`。

> ChatGPT 网页内部接口没有公开稳定的第三方限流配额，因此无法保证服务端永远不返回请求过多。v0.5 的策略是尽量减少自动请求，并在第一次被限流时立即停止批量请求，而不是继续重试。
